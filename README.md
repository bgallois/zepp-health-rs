# zepp-health-rs

`zepp-health-rs` is a Rust client, local SQLite archive, stable health API,
and MCP server for retrieving personal health data from Zepp Cloud.

The Zepp Cloud endpoints used here are unofficial and reverse-engineered. The
project preserves raw responses and marks inferred field meanings explicitly.
It does not implement Zepp login or token refresh.

## Development and AI-use disclaimer

This project was developed collaboratively with AI assistance. The project
owner defined the product direction, milestone and API requirements, and
directed the implementation. AI proposed implementation approaches, wrote and
revised Rust code, tests, and documentation, and helped troubleshoot MCP
behavior. The project owner reviewed the changes and the AI tested the observed
Zepp endpoints together, including their cache and date-range behavior.

The project owner supplied credentials and configuration choices, account data
and observed payloads, and final acceptance decisions. AI-assisted changes are
not presented as independent authorship or as proof that undocumented Zepp
behavior is universally valid.

AI assistance is not an authority for the Zepp protocol or for health
interpretation. The following are project evidence rather than AI-generated
facts:

- API behavior covered by checked-in fixtures and passing tests;
- values returned by the user's Zepp account and stored in the local cache;
- the documented cache/provider synchronization behavior;
- conclusions explicitly labelled as observed, inferred, or unknown.

The Zepp Cloud health endpoints are unofficial and may vary by account,
device, region, date range, or server revision. A successful test verifies only
the tested payload and path; it does not prove universal compatibility.

## What it provides

- Zepp API access with regional host support.
- SQLite persistence with source metadata and synchronized-range tracking.
- Cache policies: `CacheOnly`, `CacheFirst`, and `Refresh`.
- Stable health representations for HRV, heart rate, sleep, activity,
  readiness, respiratory rate, event streams, and sport statistics.
- A local stdio MCP server with a common `get_timeseries` interface plus raw
  event, band-data, sport-statistics, and summary tools.

The MCP event tool can retrieve observed streams such as readiness, Charge,
PAI, SpO₂, exertion, DailyHealth, respiratory rate, and stress. The raw event
payload is retained so new fields can be interpreted later.

## Requirements

- Rust stable (edition 2024).
- A Zepp account with data available in Zepp Cloud.
- An `apptoken` and account `userid` obtained from your own authenticated
  Zepp browser session.

## Configuration

The client reads these environment variables:

| Variable | Required | Meaning |
| --- | --- | --- |
| `ZEPP_TOKEN` | yes | Zepp `apptoken` header value |
| `ZEPP_USER_ID` | recommended | Numeric Zepp account identifier |
| `ZEPP_HOST` | recommended | Regional API host, for example `api-mifit-de2.zepp.com` |
| `ZEPP_BASE_URL` | fallback | Full API origin if `ZEPP_HOST` is not set |
| `ZEPP_DB_PATH` | no | SQLite path; defaults to `./zepp-health.sqlite3` for MCP |

Do not put these values in source code, fixtures, shell history, issue reports,
logs, MCP responses, or Git. Treat the token like a password and rotate it if
it is exposed.

## Getting the Zepp token and user ID

The values are not generated by this project. A commonly used ZeppBridge
workflow is:

1. Open Zepp's watch-face website in a desktop browser.
2. Sign in using the account that owns the health data.
3. Open Developer Tools and select the **Network** tab.
4. Reload the page or open a page that loads account data.
5. Inspect an authenticated Zepp API request.
6. Copy the request header named `apptoken` as `ZEPP_TOKEN`.
7. Copy the account identifier used by the request, commonly the `userid`
   query parameter or the authenticated user path, as `ZEPP_USER_ID`.
8. Identify the regional hostname from the request URL and set it as
   `ZEPP_HOST`.

The exact request and host vary by account region and may change when Zepp
updates its website. Do not copy cookies, passwords, or full request exports
when only the token and user ID are needed. Never paste the token into ChatGPT,
Codex, an issue, or a public terminal transcript.

Example shell setup (keep this local and private):

```bash
export ZEPP_TOKEN='replace-with-your-token'
export ZEPP_USER_ID='replace-with-your-user-id'
export ZEPP_HOST='api-mifit-de2.zepp.com'
export ZEPP_DB_PATH="$PWD/zepp-health.sqlite3"
```

## Library usage

Run the normal test suite:

```bash
cargo test
cargo clippy --all-targets --all-features -- -D warnings
```

The stable health API applies the same cache behavior to synchronized queries:

```rust
use zepp_health_rs::{
    api::ZeppApiClient,
    health::{CacheMode, HealthClient, TimeRange},
    store::Store,
};

let source = ZeppApiClient::from_env()?;
let store = Store::open("zepp-health.sqlite3")?;
let health = HealthClient::new(store, source);

let range = TimeRange::new(start_ms, end_ms)?;
let hrv = health
    .hrv(range, CacheMode::CacheFirst, now_ms, Some(86_400_000))
    .await?;
```

`CacheFirst` reads a covered range from SQLite and fetches only when coverage
is missing or stale. `CacheOnly` never contacts Zepp. `Refresh` fetches again
and updates the local records.

## Running the MCP server

Start the newline-delimited JSON-RPC server with:

```bash
cargo run --release -- mcp
```

The process reads MCP requests from stdin and writes responses to stdout. It
must be kept running by the MCP client. It advertises:

- `get_timeseries`: time-series data selected by `metric`, including `hrv`,
  `resting_heart_rate`, `heart_rate_detail`, `sleep`, `activity`, `steps`, `calories`, `weight`, `readiness`,
  `respiratory_rate`, `charge`, `spo2`, `exertion`, `daily_health`, `stress`,
  `sport_load`, and `vo2_max`.
- `get_summary`: authoritative processed summaries such as
  `resting_heart_rate`, `sleep_hrv`, `hrv_score`, `sleep_score`, daily steps,
  daily calories, weight, sport load, and VO₂ max.
- `get_events`: a structured event stream selected by `event_type` and
  optional `sub_type`.
- `get_band_data`: detailed daily records with minute heart rate, sleep,
  steps, calories, distance, activity segments, and raw activity data.
- `get_sport_statistics`: sport-load or VO₂-max statistic records, when the
  account exposes them.

The time-series and event tools accept:

```json
{
  "start_ms": 1790812800000,
  "end_ms": 1790899200000,
  "cache_mode": "cache_first",
  "recent_refresh_ms": 86400000
}
```

Daily band and sport metrics additionally require `from_date` and `to_date`.

Agents should use `get_summary` first for named metrics. They should use
`get_timeseries` only when detailed samples, custom aggregation, or a
correlation analysis is required. For example, answer “what was my nocturnal
RHR this week?” from `get_summary(metric="resting_heart_rate")`; use detailed
heart rate only for questions about intraday patterns.

For named summary metrics, prefer the processed provider stream. For example,
`metric="resting_heart_rate"` reads the nightly `sleepRHR` value from
`readiness/watch_score`; it should not be reconstructed by averaging detailed
heart-rate samples. Use `metric="heart_rate_detail"` only when you want intraday
heart-rate detail or a custom calculation.

`get_events` additionally requires `event_type`, for example:

```json
{
  "event_type": "Charge",
  "sub_type": "real_data"
}
```

## Connecting an AI agent

### Local MCP clients

Most desktop agents that support MCP accept a stdio server definition. Use the
absolute path to the repository and pass the environment variables through the
client's secret/environment configuration, not as command-line arguments.

Conceptual configuration:

```json
{
  "mcpServers": {
    "zepp-health": {
      "command": "/absolute/path/to/zepp-health-rs/target/release/zepp-health-rs",
      "args": ["mcp"],
      "env": {
        "ZEPP_TOKEN": "stored-in-your-secret-manager",
        "ZEPP_USER_ID": "your-user-id",
        "ZEPP_HOST": "api-mifit-de2.zepp.com",
        "ZEPP_DB_PATH": "/absolute/path/to/zepp-health.sqlite3"
      }
    }
  }
}
```

The exact settings screen and configuration filename differ between Claude,
Cursor, VS Code, Codex, and other MCP clients. The important properties are
the executable, the `mcp` argument, and the private environment variables.

For Codex CLI, add the environment directly to `~/.codex/config.toml` (TOML
does not expand `$ZEPP_TOKEN` from your interactive shell):

```toml
[mcp_servers.zepp-health]
command = "/home/guest/Codes/zepp-health-rs/target/release/zepp-health-rs"
args = ["mcp"]
env = {
  ZEPP_TOKEN = "replace-with-your-token",
  ZEPP_USER_ID = "replace-with-your-user-id",
  ZEPP_HOST = "api-mifit-de2.zepp.com",
  ZEPP_DB_PATH = "/home/guest/Codes/zepp-health-rs/zepp-health.sqlite3"
}
```

Keep this file private and restart Codex after changing it. Stdio MCP servers
run as a separate process and require credentials in that process environment.

## Example: “Can you correlate my HRV rise with something in my data?”

Ask the agent a question such as:

> Can you correlate my HRV rise over the last 14 days with changes in sleep,
> training load, Charge, respiratory rate, and activity? Show the dates and
> data used, distinguish correlation from causation, and flag missing data.

The agent should then:

1. Call `get_timeseries` with `metric="hrv"` for the 14-day period.
2. Call `get_events` for `readiness/watch_score` to obtain nightly HRV,
   sleep RHR, and readiness scores.
3. Call `get_events` for `exertion/algo_result`, `Charge/real_data`, and
   `RespiratoryRate/real_data`.
4. Call `get_band_data` for minute heart rate, sleep, activity, steps, and
   calories; call `get_sport_statistics` for `SPORT_LOAD` or `VO2_MAX` when
   available.
5. Align values by date, report coverage and missing intervals, and calculate
   simple comparisons or correlations.

The agent should not claim that a correlation proves that training, sleep, or
any other factor caused the HRV change. This project exposes measurements and
provenance; interpretation remains the responsibility of the calling agent.

## Privacy and security

This project handles sensitive personal health data. Recommended practices:

- Keep the SQLite database private and encrypted at rest where appropriate.
- Restrict file permissions on the database and MCP configuration.
- Use a dedicated local account or secret manager for the token.
- Do not commit `zepp-health.sqlite3`, tokens, cookies, or raw personal data.
- Review MCP tool calls before granting an AI agent access to the database.
